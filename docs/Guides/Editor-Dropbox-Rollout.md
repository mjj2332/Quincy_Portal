# Editor Dropbox rollout

Implementation is opt-in. No production migration, folder linking, webhook replay, or feature activation is performed merely by building or deploying this code.

## Confirmed workflow

- Editor workspace: `/Editor/01_ACTIVE EDITS`.
- New Project root: `2026-10 October/01/<Tonomo project folder name>`, based on the scheduled shoot's civil date. September 2026 stays `09. September`; January 2027 is `2027-01 January`.
- Children: `0. Input`, `1. Output`, `Editing Notes` for every tree the Portal creates. A mapping keeps whichever spelling it was established with (the studio's hand-made folders are mostly plain `Input`/`Output`); reviewed linking and scaffold resume recognise both spellings, and nothing is renamed in Dropbox. A ready mapping's path follows the Project's shoot date when it is rescheduled (see Reschedules below).
- Input imports DNG/JPEG originals into RAW review; Output imports edited JPEGs without assuming one output equals one original. Importing is not client publication.
- Existing active Projects require reviewed folder identity. Exact date/name matches are suggestions, not authority. An Admin can provide an explicit reviewed alternate for a legacy name/date without moving files.
- Tonomo RAW paths remain separate, preserving AutoHDR identity. A ready Editor mapping takes over I/O. Pending/review mappings retain legacy RAW intake where available, but do not permit edited publication into an unverified destination.
- Portal's own exports use `Manual-Uploads/<asset-id>/<filename>` below Input/Output. This is a reserved echo-suppression subtree; users should place externally edited files elsewhere under Output.

## Activation order

1. Back up production D1 and review migration `0041_editor_folder_mappings.sql`. It adds a table and indexes, with no rebuild of Projects.
2. Deploy background, webhook-ingress, then app with `DROPBOX_EDITOR_AUTOMATION_ENABLED="0"` in both background and app. Validate existing behavior before activation.
3. Review active Project candidates using `GET /api/integrations/dropbox/editor-folders?cursor=<optional UUID>`. Pages contain at most 25 Projects. Unresolved entries are `needs_review`; never guess an address match. Legacy Projects hand-named outside the derived path (`<month>/<dd>/<Tonomo RAW leaf>`) are inspected instead with `POST /api/integrations/dropbox/editor-folders/inspect`, body `{ "projectId": <uuid>, "rootPath": <the hand-named Editor root> }`; `derivedRootPath` in the response shows what automatic discovery would have used, for comparison against the reviewed root.
   - `projects.shoot_date` must be a canonical `YYYY-MM-DD`; rows still showing `needs_review` with "Invalid shoot date" are `awaiting_raw` legacy rows pending the follow-up migration.
4. Link a reviewed candidate with `POST /api/integrations/dropbox/editor-folders/link`, body `{ "reviewed": true, "candidate": <reviewed object> }`. This endpoint requires `manageIntegrations`, validates current Project snapshots, and re-reads exact Dropbox folder IDs and paths. An established mapping cannot be relocated through linking. The `candidate` object from a `POST …/editor-folders/inspect` response (when `status` is `"candidate"`) is pasted verbatim as this endpoint's `candidate` body.
5. Auto-creation is on: background `EDITOR_AUTOCREATE_AFTER_MS` is `"1"` (epoch milliseconds) since 2026-09-15, so every unmapped Project created after that instant, which is all of them, gets its Editor tree created automatically once it meets the scaffold prerequisites (not archived, not `delivered`, ISO `shoot_date`, an active photographer member, no queued or running RAW sync for the Project, a RAW folder that resolves). A Project whose Editor root already exists in Dropbox goes to `needs_review` for reviewed linking instead of being recreated. Setting the value back to `"0"` disables automatic creation for unmapped Projects without touching existing mappings. When the stored Tonomo RAW path no longer exists, the scaffold tries the Project's RAW shared link: a folder found under `/Tonomo/Raw Files` (never the root itself) with the same address leaf is adopted onto the Project (audit `project.raw_folder_path.changed`, AutoHDR re-scaffold, RAW sync) and the tree is created on the next reconcile, after that sync has scanned the folder, since a ready tree takes RAW intake away from the Tonomo folder; a folder found elsewhere is never adopted, because that Project was completed and delivered outside the Portal and should be marked delivered or archived; if the folder is gone, the tree is still created and named from Tonomo's original-cased formatted address (else the Project's own address), with `rawSource: "missing"` on the mapping and in the candidate endpoint. RAW for such a Project arrives only through its Editor Input root. Every pass that stops short of a ready tree leaves its reason on the `editor_reconcile` job (`jobs.error`, status stays `done`; the Project workspace's job list shows it as "Editor folder"), and the candidate endpoint repeats the latest one as `lastReconcile` on unmapped and pending items, so "done, no tree" is never silent (a `needs_review` mapping re-stamps its conflict reason on every hourly pass, which is intended: the latest job always states the current blocker). Reasons are prefixed with a stable code: `no_shoot_date`, `no_active_photographer`, `raw_identity_unavailable`, `raw_leaf_mismatch`, `raw_outside_root`, `raw_path_recovered`, `raw_path_change_lost`, `raw_sync_in_flight`, `provision_lease_held`, `project_not_provisionable`, `project_inactive`, `needs_review`, `autocreate_not_allowed`. A ready tree's reschedule move has its own `editor_folder_move_*` codes and its own `editor_folder_moved` success note — see Reschedules below. A declined Tonomo RAW path change is recorded as audit `project.raw_folder_path.declined` with the stored and incoming paths and the reason (deterministic declines only; transient Dropbox failures are retried by the webhook and stay in logs). There is no automatic retry beyond the hourly recovery pass, which re-enqueues every unmapped active Project.
6. Enable `DROPBOX_EDITOR_AUTOMATION_ENABLED="1"` in both Workers for the pilot. Linking while enabled enqueues an initial sync so files that predate the monitor cursor are not missed. A mapping linked while disabled retains a pending initial-sync marker; the minute recovery scan enqueues it after activation. The marker is completed only after both Input and Output finish their bounded scans. Review DNG previews and file counts before expanding the batch.
   - Pilot completed 2026-09-14 on one `editing_autohdr` Project: the Editor monitor durable object bound to `/Editor/01_ACTIVE EDITS` and the initial sync ingested Input and Output on the first run. The flag is now `"1"` in both committed `wrangler.jsonc` files, so a redeploy no longer turns Editor automation off.
7. Monitor `GET /api/integrations/dropbox/monitors/editor` and the Project jobs endpoint. Failed Editor jobs can be retried through the existing Admin job retry endpoint. The Editor cursor is independent of RAW and AutoHDR.

## Reschedules

A Tonomo webhook that carries a different day for a Project whose `shoot_date` is already canonical moves the date only when the source identifies a real calendar date: `when.start_time` rendered in the property's timezone, ISO text, or Tonomo's display text with its weekday cross-checked (`shootDateSource` on the parsed order). The write is one fenced D1 batch (`projects.shoot_date` guarded on the value the processor read and on no accepted change coming from a webhook received later than this one, compared by receipt time, so a redelivered older event never rolls a reschedule back) with audit `project.shoot_date.changed` (actor `tonomo`, `previousShootDate`, `shootDate`, `orderId`). Unparsed text against a canonical date is never written; it is recorded once per stored date and distinct text as audit `project.shoot_date.declined`.

**The Editor tree moves.** A `ready` mapping (derived or hand-linked — `reviewed_by` set) whose stored `shoot_date` differs from the Project's is relocated to the new day folder: `<EDITOR_ROOT>/<month(new)>/<day(new)>/<leaf>`, keeping the tree's existing leaf name and casing verbatim (a hand-linked mapping's own name is never renamed to the derived form). The old day folder is left behind, empty, never deleted — this is deliberate, not a bug, in case an operator still needs to look at it. Delivered/archived Projects never *start* a move, though a move already under way is finished even if the Project is archived or delivered mid-flight, so it never lands half-relocated. A move is only ever computed relative to the tree's *own* current day folder: if that folder's parent is not exactly the derived day folder for the mapping's own stored (old) `shoot_date`, the Portal does not guess a new location — it blocks with a visible note instead (see codes below), because guessing wrong here would silently strand Input/Output routing.

Two safeguards exist because a human can drop files into the tree at any moment, and Dropbox reports each file's `server_modified` only when the Portal next asks — there is no push signal. Before claiming a move, the Portal requires 30 minutes with no file in the tree modified more recently than that; it checks once more immediately after claiming (in case an upload landed in the gap) and, if one did, releases the claim and lets a later pass retry the whole check. After a move lands, the now-empty old path is watched for another 30 minutes: if anything reappears there (a client's sync client, a straggling upload that started before the move but finished after), the Portal reports it in a visible note — it never merges or adopts those files into the new location — and stops watching once the 30 minutes are up. Move it into the new tree by hand.

A job or a RAW reconciliation claim already working the Project blocks a move from starting: `editor_sync`, `dropbox_sync`, `manual_edited_publish`, `manual_raw_publish`, and the AutoHDR send jobs, while queued or running and updated within the last two hours. Past two hours with no progress, the job stops blocking (a stuck job must not wedge every future reschedule forever) and gets a one-time visible note on its own `jobs.error` — `stale_job: no progress for 2h; no longer blocks the Editor folder move` — without touching its status or `updated_at`, so it is never mistaken for real progress.

The claim itself, the eventual commit, and every writer that touches a mapped tree in between are fenced on `root_revision`, a counter the mapping's commit bumps by exactly one. This is a version fence, not just a path fence, because a mapping's root path key can in principle cycle back to a value it held before (A → B → A across two reschedules); a writer bound only to the old key could otherwise match a *later* occupation of that same key. `sync-output.ts` and the RAW-mapped branch of `dropbox/sync.ts` read the revision once at the start of a run and bind every subsequent write to it, plus a live `move_status != 'moving'` check, so a run that starts before a move and is still writing when the move lands cannot land under the new tree; a mapping caught mid-move is instead a clean no-op (RAW sync ends its job `done` with note `editor_folder_move_in_flight`; it and Output resume on the next scheduled pass). Manual publish (`manual-edited-publish.ts`) refuses outright while a mapping is moving — `Editor folder for project <id> is moving; manual publishing resumes after the move` — so a publish caught mid-move ends failed rather than pending, and an operator's retry afterwards resolves against the tree's new path.

Landing a move is one D1 batch: the mapping's own root path/key/`shoot_date`/`root_revision` together with every Dropbox path this Project has recorded elsewhere — Edited/RAW asset `source_path`/`source_path_key`, ingest identity keys, edited-source-claim keys, the editing-notes path, and the recovery-proof trail — rebased from the old root onto the new one in the same batch, gated on this exact move having just landed so a retried batch after a partial failure is a no-op rather than a second rebase. `reviewed_by`/`reviewed_at` are never touched by a move. Audit `editor_folder.moved` records the mapping, both roots, both shoot dates, the Dropbox folder id, the new revision, whether the mapping was hand-linked, and any job ids the move found and marked stale.

**Blocked and deferred notes an operator may see**, all on the `editor_reconcile` job (`jobs.error`, status stays `done`), and for a blocked or stuck move also on the mapping's `move_note`:
- `editor_folder_move_nonstandard_parent` — the tree's current parent does not match the day folder its own stored shoot date derives to. Move the folder by hand into that expected day folder; the note names both. Once it agrees, the next reconcile computes the move to the new date normally.
- `editor_folder_move_conflict` — a folder already occupies the destination name, or another mapping already holds or is targeting that path. Resolve the name collision (rename in Dropbox, or decide which Project should own it) and the next pass retries.
- `editor_folder_move_source_missing` — the mapping's Dropbox folder id no longer resolves to anything. Restore or relink the root.
- `editor_folder_move_moved_elsewhere` — Dropbox reports the tree somewhere the Portal never expected (neither the old nor the new location). The Portal never adopts it; find it and resolve by hand.
- `editor_folder_move_deferred` — a blocking job, an active RAW reconciliation claim, the upload quiet period, or a concurrent reconcile pass. Not an error; no action needed, a later pass retries automatically.
- `editor_folder_move_in_flight` — another pass already holds the move's ten-minute lease. No action needed; a stalled lease is taken over automatically once it expires.
- `editor_folder_move_orphan_upload` — a file appeared under a root a move vacated. Move it into the mapping's current root by hand; the Portal will not merge it for you. Then acknowledge the report under Admin → Pipeline → *Needs attention*. Every landed move watches the root it left for 30 minutes (#195); an empty folder that reappears there does not count. A watch that finds nothing ends by itself, but a report stays listed until someone acknowledges it. Acknowledging does not re-check Dropbox: it records, in audit `editor_folder.move.orphan_upload.acknowledged`, that an admin has dealt with the files.

  *Deploying #195.* Apply migration 0046 before deploying the background worker: the new worker reads only the new table. A move the old worker commits in between lands in the retired `moved_from_path` column, which nothing reads now. Once the new worker is live, run `portal/scripts/0046-legacy-orphan-watch-drain.sql` once with `wrangler d1 execute`. It copies any such watch across and clears the column; with nothing to copy it does nothing. A copied watch takes the negated revision (`-root_revision`), so it never collides with a watch the new worker wrote after moving that tree again. Nothing needs resolving by hand. If it reports an error, never run its `UPDATE` on its own: until a watch row exists, the column is the only record of that old root. Report the error instead.
- `editor_folder_move_refused` — Dropbox refused the relocation itself (permissions, quota, too many files). The note carries Dropbox's reason; fix it in Dropbox and the next reschedule retries.
- `editor_folder_move_stuck` — the tree has already moved in Dropbox but the Portal failed to record the move three times in a row. The mapping is deliberately held in `moving`, so Output sync, manual publishing and RAW reconciliation for that Project stay off until an operator reconciles the database with Dropbox by hand. Nothing retries it.

**Where to find these without reading jobs** (#163). Admin → Pipeline → *Needs attention* lists every Project whose mapping is latched, most severe first: `stuck` and `overdue` (a `moving` row whose lease expired more than two hours ago, or has no expiry, and that nothing is taking over), then `needs_review`, then a `blocked` move that still applies on a Project that is neither archived nor delivered: its target date is still the Project's date, or its code is `_moved_elsewhere`/`_source_missing` (the recorded root is dead whatever the date does). A `moving` row whose lease expired less than two hours ago is not listed: the cron takes it over within minutes. The Project page shows the same state as a banner to staff, with the diagnostic only for admins; photographers never see it. The same panel shows the External Editor provisioning freeze (#161), which is released from Admin → Users. Orphan-upload reports come last, one row per report and on any project, archived and delivered included. They are the one row the panel can clear: *Acknowledge* removes it. Every other row clears when its underlying state does. The Project page banner shows an orphan upload only when the mapping has no latch of its own. A watch on a mapping that is stuck, overdue or in review is not checked until the mapping is ready again.

A `pending` mapping that has created nothing in Dropbox yet is still re-pointed at the new day folder inside the provisioning lease, using the shoot date re-read under that lease, before anything is created — this part is unchanged from before the move landed. If a root already exists at the old path without a recorded id (a pass that died mid-create), it is not re-pointed and goes to the existing-root review instead; if another Project already holds that root the mapping goes to `needs_review`, and if the mapping changed under the lease the pass ends with `provision_lease_held` and the next pass re-reads it with "Editor root for the new shoot date is already mapped to another Project". A Project deadline (`project-deadline.ts`) is its own saved Sydney civil time and never reads `shoot_date`, so a reschedule does not move the deadline or its reminders; staff adjust it by hand. The stale-event guard on `shoot_date` itself only knows about changes it wrote itself: a date set at Project creation or by the display-to-ISO upgrade carries no receipt time, a payload Tonomo sends late is judged by when the Portal received it, a poisoned event replayed from Webhook recovery can still roll back a date that a newer event confirmed without changing it, and two events received in the same millisecond have no defined order.

## Webhook recovery

The `action: "changed"` fix unwraps the nested order and validates its identity against the outer order reference. It preserves existing field-merge semantics; it does not introduce unconditional overwriting of manually populated Project fields. The four observed payloads without any order identity are a separate invalid payload class and remain visible for review.

After a deployed fix is verified, replay only the reviewed changed-event failures through the existing Admin retry workflow. Do not bulk discard invalid events or blindly replay old metadata. Replays can trigger downstream reconciliation once automation is enabled.

## DNG verification gate

Original DNG bytes remain immutable and downloadable. Browser review uses a separate cached derivative, never DNG bytes labelled JPEG. Test representative studio DNGs, including orientation and embedded-preview format, before production activation. A successful import alone does not prove a usable review preview. BigTIFF, missing previews, or unsupported preview encodings must surface a diagnostic rather than masquerade as a completed preview.

The Canon EOS R5m2 sample uses JPEG XL compression 52546 for its review-size SubIFDs. The bounded decoder accepts reduced JPEG XL previews up to 1,048,576 pixels (the verified sample is 1024×683), with 4 MiB compressed/output caps and separate 64/32 MiB decoder/encoder linear-memory caps. JPEG-embedded previews remain supported. This is an embedded-preview pipeline, not a full sensor-RAW developer; a DNG without a usable embedded preview remains an explicit preview failure with its original retained.

## Rollback

Disable the Editor flags in both Workers to stop Editor ingestion/provisioning and restore legacy routing. Keep mapping rows and files intact. This does not move files back to Tonomo or undo imported assets, so review the operational consequences with the studio before toggling. Never delete the mapping table to simulate rollback.
