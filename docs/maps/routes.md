- **Email verification (#741 13a)** `guest/email.ts` (`mountGuestEmail`, called first in `mountGuest`). `POST .../email/code {email}` mails a 6-digit code and answers 202 `{sent:true,resendAfterSeconds:60}` for every well-formed address; `POST .../email/verify {code,name}` (name 1-80 chars, one line) swaps the right code for a verified session: fills `guest_sessions.guest_id` and `verified_at`, upserts `guest_reviewers` (the last name written wins) and `guest_link_members` (`unsubscribed_at` untouched), **rotates the session token** (new `Set-Cookie`, the old cookie is dead) and answers the session body. Order: link id, gate, Origin, session; both then read the body and only then take one fresh time for every limit decision (resend minute, bucket keys and windows, reservations, Retry-After), so a body held across a window boundary is charged to the window it completes in; the entry time is used only for authentication. Codes: hashed with `lib/review-passcode.ts` (no secret), 10 minutes, 5 tries (the sixth finds no row: 401 `code_expired` even with the right code), single use, only the newest code of a session counts. Errors: 401 `code_expired`, 401 `code_incorrect {attemptsLeft}`, 409 `already_verified` (a verified session and a different address), 429 `too_many_attempts` + `Retry-After` (the longest remaining window of the full buckets). Buckets in `guest_rate_limits` (`reserveAttempts` takes a `windowMs` per bucket): send `codesend:session:<id>` 1 per 60 s, `codesend:email:<sha256>` 5 per 15 min, `codesend24h:email:<sha256>` 20 per day, `codesend:link:<id>` 30, `codesend:ip:<sha256>` 10; verify `codeverify:link:<id>` 100, `codeverify:ip:<sha256>` 30 (15-minute windows unless stated; addresses are hashed, never stored raw). The verify batch swaps the token first under every fence and each later statement runs only if the swap landed, so a revoke, replace, expiry, newer code or a double-click writes nothing (a correct verify beaten by a competing correct verify on the same session finds its session live with a rotated token and gets 401 `code_expired`, so the client refetches the now-verified session; a revoke or replace has deleted the session and is the stub). Audit `review_link.email_code_send` (meta `{guest:{sessionId}, linkId, delivered, errorCode?}`) and `review_link.email_verify` (`{guest:{guestId,sessionId}, linkId}`), never the address or the code. One fragment, `guestEmailFence` (exact token hash and identity, live link and generation, gate, unarchived Project), is carried by every write on these routes (the attempt counter, the code INSERT, the token swap; the rest of the verify batch keys on the swapped token), and `classifyRefusal` runs once right after the body is read on both routes (before 413/400) and again before every later non-success answer (each 429, `already_verified`, no code row, `code_expired`, `code_incorrect`) so a refused write is never `code_incorrect`/`code_expired`. The send audit row is written in the same batch as the code and its delivery outcome is recorded against its id afterwards, so it survives a revoke or gate close during the send. Both routes check an archived Project on entry (409 `project_archived`, before limits and body), and every committing statement repeats the live session and link at a fresh time taken after the body is read, the feature gate (master, all-projects or pilot row, `guest` part) and `archived_at IS NULL`; a refused commit is the stub, or 409 `project_archived` when only the archive landed. The email (`composeCodeEmail`) is text plus escaped HTML from `NOTIFICATIONS_FROM_ADDRESS`, carries no Review link and no unsubscribe link, and a send failure or a missing `EMAIL` binding is still 202 with `delivered:false`.
