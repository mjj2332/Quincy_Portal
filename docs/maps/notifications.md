## Staff video-review notifications (#741 15a)
- **Gate:** emitted only while the Project's `notify_staff` part is on at write time (`readVideoReviewGate`), and checked again at delivery (resolver) and at every channel admission (SQL). Dark otherwise.
- **Recipients** (read just before the source batch, one rule for every kind, `videoAudience` in the emitter): active users with a `project_members` row on the Project whose role holds `viewVideo`, never the Actor. So a reply, a note, an upload, a decision and a Release all go to the same people; a Photographer and an Admin who is not a member are never told. Every recipient, an Admin member included, is snapshotted as `project_member` with their membershipIds, so delivery re-checks membership (a legacy `{kind:'admin'}` row still delivers while the user is an Admin). A guest is never a recipient; a guest actor is the outbox `actor_id` `guest:<guestId>`.
- **No note text anywhere:** the payload holds ids only. The title is composed at delivery by `resolveVideoReviewRecipient` portal/workers/background/src/notification-delivery.ts (before the default mention branch) from the Video title, Version number and actor name; the body is static. The sentinel test in `portal/workers/background/test/video-review-notifications.integration.test.ts` fails if note text reaches `notifications.title`/`body` or the email.
- **Authorization at delivery:** `legacyAdmission` has its own branch for this event (staff and External alike): recipient active, role holds `viewVideo`, epoch, Admin-or-snapshotted-member, Project unarchived, gate open with `notify_staff`, source row live (a deleted note suppresses; a withdrawn Release suppresses `video_released`; a `video_mention` must join a live note). An External sees the row through the `project.video_review.notification` arm of `externalVisibleNotificationWhere`, so only while assigned.
- **Digest:** a deferred item is re-authorized by the same predicate (`VIDEO_REVIEW_AUTHORIZED_SQL`, portal/workers/background/src/notification-delivery.ts) in `sendDigestForRecipient` portal/workers/background/src/email-digest.ts, both as a drop rule (`video_review_reauthorization_failed`) and in the `sending` admission fence.
- **External copy (#835):** an External reads the narrowed shared copy for `video_released` ("Video review update") and `video_mention` ("You were mentioned in a video note."), naming no Video, Version or person; both channels allowed.
- **Email:** `finishEmail`, the person's cadence (not digest-exempt). Immediate-cadence tests must insert `email_digest_cadence = 'immediate'` (docs/lessons.md #489).

## Delivery unlock requests (#787 slice 8)
- **What:** a client asked, on the public Delivery page, for one locked item to be unlocked. One outbox event `project.delivery.unlock_requested`, one notification type `delivery_unlock_requested` (Edited tab until the Delivery tab exists, slice 10). Actor is the sentinel `client:delivery` (a client has no account; the resolver never looks it up). Source key `delivery_unlock_request:<auditId>`: one per request that landed, so tomorrow's request is a new notification.
- **Recipients** (chosen in the writing statement): every active Admin (payload `authorizationAtOccurrence: {kind: "admin"}`, no membership needed) and every active Editor with an `editor` membership on the Project (`{kind: "project_member", membershipIds}`). Never an External editor or a Photographer: the role must hold `manageExtras`, at write and again at delivery. External policy `suppressed` (`delivery_withheld`), no External copy, no External channel, no arm in `externalVisibleNotificationWhere`.
- **In app only; email off.** The writer inserts an `in_app` ledger row and NO `email` row, so `finishEmail` finds nothing to begin and sends nothing even for an Immediately cadence; `deferEmailToDigest` finds no email ledger row to digest. There is therefore no digest item to re-authorize (`email-digest.ts` is untouched on purpose). If an email channel is ever wanted: add the `email` ledger row, a `DELIVERY_UNLOCK_AUTHORIZED_SQL` drop rule beside `videoReviewUnauthorized`, and decide digest-exempt.
- **Authorization at delivery** (`resolveDeliveryUnlockRecipient` and `legacyAdmission`, both from `DELIVERY_UNLOCK_AUTHORIZED_SQL` in `portal/workers/background/src/notification-delivery.ts`): recipient active and `manageExtras`; epoch; Admin snapshot still an Admin, or a snapshotted membership still held (`membership_removed`, `membership_cycle_changed`); an archived Project does NOT suppress (the public page keeps serving); Client Delivery gate open; the request's audit row present; the page's latest set STILL the set the request was made on (`set_replaced`: the payload records `setNumber`, and the copy's label such as "Photo 07" is only true of that set, so a newer Publish suppresses it even if the asset is still present under another label), the item STILL in that set (`item_not_published`) and STILL locked (`item_unlocked`: a fulfilled request is not news). A page switched off since does NOT suppress. The lock test is `deliveryLockedSql` (`workers/background/src/delivery-lock-sql.ts`), pinned to the app's `lockedSql` by `test/delivery-lock-sql.guard.test.ts`.
- **Copy:** title `A client asked to unlock Photo 07` (the label the page shows, carried in the payload), body names the street. No filename, no client identity.

## Client hourly digest (#741 15b)
Not the outbox: guests have no `user` row. Rows in `guest_notification_digest`, one email per subscribed membership per hour, composed at send time by the background Worker.
- **Producers** (app Worker, `portal/workers/app/src/lib/guest-digest.ts` `guestDigestStatements`, ids from `lib/sql-uuid.ts` `SQL_UUID_V4`): one `INSERT ... SELECT` per event, appended to the source write's batch and fenced on its audit row. The gate (`video_review`, scope, `guest`, `notify_client`) is inside the statement. Sites: `addLinkVideo` (`video_added`) and `setLinkGrants` (`version_granted`, only grants the write inserted) in `lib/review-links.ts`; `createVideoNote` (`public_note`: a STAFF root note with `visibility = 'public'`) and `createVideoNoteReply` (`staff_reply`: a staff reply under a public root, to the guests who authored the root or a reply) in `lib/video-notes.ts`; `releaseVersion` (`video_released`: links with a live grant and `allow_download`) in `lib/video-approval.ts`. Internal notes and replies, a guest's own writes, edits, deletes and staff-recorded decisions produce nothing.
- **Flush** `runGuestDigests` portal/workers/background/src/guest-digest.ts on the `0 * * * *` cron, after `sweepGuestDigests` (pending rows older than 7 days and unsubscribe tokens older than 180 days are deleted). Per membership, in this order: claim by CAS on `last_digest_sent_at` (55 minute window, `changes() = 1` owns the slot); snapshot the pending ids; mint a fresh unsubscribe token (hash only) and load the label; then **the fence**, ONE batch that is the last database step before `EMAIL.send`: it marks `sent_at` on exactly the snapshot rows that still pass the re-filter (link live against the real `Date.now()`, not the cron's scheduled time, which is only bookkeeping; gate with `guest` + `notify_client`; member subscribed; Video a live member; Version live-granted; note still public staff text and undeleted with a public root; Release live with downloads on) while this run still owns the slot, reads those marked rows back, and marks the rest of the snapshot dropped. The email is composed from the marked rows only. No survivors: no email, the slot is given back. **At most once, by ordering:** rows are claimed BEFORE the send (settled decision 10's "written after the send" moved earlier on purpose), so a crash or a failed write after sending can never un-mark them or cause a resend. A fence batch that throws (including one that committed but lost its reply) releases this run's marked rows and the slot, since no send was attempted. A Worker interruption between the fence batch and `EMAIL.send` loses that hour's items without a send attempt; this is accepted, because an attempt marker cannot tell 'stopped before the send' from 'stopped after it', and the second must never resend. Definite rejections are released for retry; ambiguous outcomes are treated as sent. A throw with no code, an unknown code, a timeout or `E_DELIVERY_FAILED` stays marked, and so does a rejection tied to the recipient or the message (suppressed, invalid address, too large, bad headers), which would only repeat. A code in `DEFINITE_REJECTIONS` (guest-digest.ts: rate or daily limit, or a sender-side setup error the owner can fix) proves the message was not accepted and a later run could succeed, so one UPDATE sets `sent_at = NULL` on this run's fenced rows only (`sent_at` still equals this run's real-clock stamp) and the member's `last_digest_sent_at` goes back to its prior value only while it still holds the stamp; the next run retries. If that release write fails, a safe code is logged and the rows stay marked. Eligibility (the 55 minute cooldown) and every recorded timestamp use the real `Date.now()`, not the cron's scheduled time. After a send that returns successfully or throws ambiguously, one best-effort UPDATE moves the member's `last_digest_sent_at` to a fresh `Date.now()` (only while it still holds this run's pre-send stamp; `sent_at` is untouched), so a slow send cannot shorten the 55 minute cooldown; if it fails the pre-send stamp stays and a bounded message is logged. A send failure is only logged (bounded reason, no address). A missing `EMAIL` binding or sender skips the run and claims nothing.
- **Email** (sender `NOTIFICATIONS_FROM_ADDRESS`): subject `Updates on <label or "your video review">`, grouped by Video, at most 50 item lines (then "and N more"), excerpts of public staff text at most 280 characters, HTML escaped, `List-Unsubscribe: <url>`. It carries NO Review link. The one URL is `${APP_ORIGIN}/d/unsubscribe#t=<token>`; the unsubscribe routes are in `docs/maps/routes.md` ("Client digest subscription").
- Tests: `workers/app/test/guest-digest-producers.test.ts`, `guest-subscription.test.ts`, `workers/background/test/guest-digest.integration.test.ts`.
