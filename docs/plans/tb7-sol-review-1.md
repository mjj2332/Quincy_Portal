# TB7 Notice Board migration — fresh Sol review 1

## Blocking issues

1. **The plan is intentionally not build-ready while §4 remains unresolved, and the governing scope currently requires the durable path.** The source confirms the plan's diagnosis: both Notice Board create and edit call `notifyNoticeBoardMentions()` after their post/mapping batch (`portal/workers/app/src/routes/notice-board.ts`), and that helper calls legacy `emitNotifications()` directly (`portal/workers/app/src/lib/notifications.ts`). `emitNotifications()` durably inserts the in-app `notifications` row but only attempts email best-effort; it creates no `notification_outbox` or delivery-ledger row. `notification_outbox.project_id` is `text NOT NULL` in both `schema.ts` and migration 0031. The TB4 implemented plan explicitly left Notice Board mentions on this direct path. Thus the claimed mismatch is real, not hypothetical.

   The two proposed outcomes are semantically sound, but they are not equal under current authority. The TB7 roadmap says both "Reuse TB4 durable mention delivery" and "durable mention delivery" in acceptance, while architecture §9 requires durable mention delivery. Choosing read-state-only therefore requires an explicit authority change to both documents (and the revamp brief/index wherever they repeat the promise), not merely softer wording inside this implementation plan. Choosing durable delivery requires a separately reviewed global-event outbox design; it is not a small conditional tail of a read-marker build.

   There is no clean migration-free third technical option. A sentinel/fake `project_id` would avoid the `NOT NULL` migration but would falsify the column's domain and collide with resolver/index/admin assumptions. A second Notice-Board-only outbox would duplicate TB4's ledger/recovery machinery. The simpler *delivery decomposition* is to name and approve a TB4F-style global-outbox prerequisite, ship it first, then make TB7 itself a two-slice read-state/frontend migration. That is scheduling, not a third data model.

2. **If durable delivery is selected, §4 does not yet specify enough of the required contract to approve its addendum or estimate slice 3.** The addendum must explicitly cover:

   - a Notice Board event/payload type and the exact reauthorization rule (`active` plus current `viewNoticeBoard`, exclusion of `external_editor`, authorization-epoch behavior, and self suppression);
   - mapping/source-key validation and what removal of a mention before delivery does;
   - nullable/global `project_id` behavior through every background claim, resolve, admission, in-app insert, retry, and recovery query;
   - the roadmap's "Admin operations" promise: existing delivery list, replay, discard, safe labels for a global event with no project street, and safe error codes; and
   - transactional producer admission plus queue publication after commit for both create and newly-added edit mentions.

   The current background resolver is strongly project-shaped and its row types declare `projectId: string`; changing only the table nullability and adding one resolver branch is not enough. Until this is designed, "three slices" conceals a cross-worker migration rather than bounding it.

## Should-fix issues

1. **Add client-side response-order fencing for the read-state query.** The plan mirrors TB3's server upsert and presentation proof, but it omits TB3's separate `commitProjectCommentReadState()` protection: monotonic marker/latest tuple comparison plus request-start sequencing when tuples tie. A slow GET begun before a successful PATCH (or another device's later marker) must not overwrite the newer cached state and resurrect a stale badge/unread count. Add this contract and a reversed GET/PATCH completion test; the existing "reverse old/new fetch completions" test only discusses posts/presentation attempts.

2. **Reconcile migration authority as part of the plan.** `0038_project_activity_feed_index.sql` is genuinely the last migration file and journal entry, and `docs/todo.md` records it applied to production on 2026-08-31, so `0039` is the correct next number on the inspected tree. However, root `CLAUDE.md` still ends the migration ledger with 0037 and says the next number is 0038. Because `CLAUDE.md` says it is mirrored verbatim to `AGENTS.md`, the implementation documentation slice must update both after the normal production-ledger recheck. The plan's current "three sources" statement is factually correct only because it names the directory, journal, and todo; its broader authority/process story is incomplete while root authority is stale.

3. **Reshape §5 after §4 is decided.** If scope is read-state-only, there are two implementation slices plus an authority/docs correction, not a meaningful third code slice. If durable delivery remains acceptance, the global-outbox prerequisite needs its own reviewed schema/background/Admin-operations slices and deployment order; it should not be compressed into one conditional "resolved mention boundary" slice. The current breakdown cannot be right-sized for both outcomes.

4. **Keep viewport proof, but reduce it to the Notice Board's actual lifecycle.** `NoticeBoard` sits immediately below the Dashboard pagehead, but it can show 50 newest-first posts and the whole page scrolls. A user can be reading lower notices or the project board while a poll inserts a new head above the viewport, so `open + visible document + focused` alone would falsely mark that head read. Some real viewport proof is proportionate and satisfies the roadmap/architecture's "visibly presented" rule.

   Do not, however, copy TB3's whole project lifecycle apparatus. TB3 handles a paginated discussion inside changing project/route/access presentations and an optional scroll root. Notice Board has one global head, one Dashboard placement, no pagination, and a provider already keyed by principal/authorization epoch. A compact observer of the actual newest-post surface (or a deliberately non-zero top sentinel), focus/visibility refs, one presentation generation, and one fresh-fetch attempt token is enough. The current wording's "stable anchor immediately before" the posts is underspecified: an empty zero-area anchor can never satisfy the required positive-area intersection.

5. **Tighten the high-water rationale, while retaining the invariant.** The conditional marker upsert SQL is correct: it resolves the post tuple server-side, advances only lexicographically newer `(created_at, id)` tuples, and leaves `updated_at` unchanged on equal/older targets. A single global stream does not eliminate the same-millisecond hazard: two concurrent Worker requests can compute the same `new Date()` before D1 serializes their writes, and a later-committing lower UUID would sort behind a marker for the first post. Allocating `created_at` in the INSERT from `MAX(wall clock, MAX(posts)+1)` is therefore defensible even without imports/batches.

   `MAX(markers)+1` is a narrower safeguard, needed only when the former high-water post was deleted and the clock does not advance beyond its retained timestamp. The normal human create/read/delete/create path will not occur within one millisecond, but concurrent/precomputed request timestamps or clock anomalies can still violate the invariant. Keeping the marker term is cheap and makes the retained-marker design total; describe it as deletion/clock defense rather than importing TB3's per-project concurrency rationale wholesale. Tests should prove ordering semantics, not imply same-millisecond human UI actions are common.

6. **Make the post-create/read-state response contract explicit.** Slice 1 atomically advances the author's marker through the newly inserted post, but the proposed POST response remains only `NoticePost`. "Settle both exact queries from/refetch against the server response" is ambiguous. Specify either a mutation envelope containing both `post` and authoritative `readState`, or a mandatory read-state refetch after the post response. The former gives the promised immediate current-tab state without a second race-prone round trip; either choice still needs the response-order fence above.

7. **Clarify the documentation basis for rollback.** Root `CLAUDE.md` confirms Hono bare/trailing-slash registration and `background → webhook-ingress → app` deployment order. It does not state a general "no backfill on rollback" rule. The plan's no-localStorage-backfill and leave-additive-table-on-app-rollback approach is nevertheless safe and conservative: old code ignores the table and a later TB7 redeploy retains marker data. Present this as a plan decision justified by additive compatibility, not as an existing documented convention.

## Nits

1. The factual current-state inventory is otherwise accurate: collapse/read storage keys, 25-second expanded poll and 60-second collapsed latest poll, unconditional `markSeen()` after successful expanded fetch, path-scoped capability middleware, newest-first tuple ordering, created-at index, no existing Notice Board marker, exact project marker schema, and the project-comment D1 batch/upsert pattern all match source.

2. The "visible presentation proof" is not in `workers/app/src/lib/project-comments.ts`; that server module contains the monotonic SQL/batch service. The generation, `IntersectionObserver`, geometry fallback, and fetch-attempt proof live in `apps/web/src/lib/project-comments.ts`. The plan itself cites `useProjectCommentPresentation()`, so this is mainly worth keeping precise in future review notes.

3. Both RichTextEditor lessons are represented accurately. `NoticeBoard.tsx` owns `content`, `editingId`, and `editingContent`, while polling replaces only `posts`; query migration, remote-edit handling, and even a deleted-edit tombstone can be implemented at the parent boundary without touching `RichTextEditor.tsx`. The stated scope boundary is achievable. Preserve editor identity while a draft is active; do not key the editor to fetched post identity.

4. Bare and trailing-slash terminal registrations should indeed be classified separately if both are added. The existing `/notice-board` and `/notice-board/*` capability middleware means a trailing-slash miss is still capability-gated today, so describe the duplicate exact routes as byte-identical API behavior plus defense against permissive fallback, not as evidence that the current Notice Board wildcard gate itself is absent.

5. `updatedAt` should use a monotonic server value if two successful advances can occur in the same millisecond and consumers interpret it as a version. Marker correctness does not depend on it, but the plan should either state it is observational metadata only or allocate `MAX(Date.now(), existing.updated_at + 1)` as existing Admin recovery code does.

**Verdict: REVISE.**
