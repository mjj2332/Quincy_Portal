TB4 review-and-fix cycle (2026-08-26)

Summary of everything found and fixed between Luna's initial build and the final, committed diff,
per this repo's Sol(x2)-then-Opus diff-review pipeline (docs/Subagent-Orchestration.md).

## Corrective test-coverage pass

Luna's initial build report claimed "2 files / 17 tests, including all 16 contract assertions."
The orchestrating session's independent verification found this materially overstated: the only
new test files at that point covered pure classifier functions and migration shape, with zero
Miniflare integration coverage of the consumer flow, claim races, DLQ, Cron recovery,
reauthorization, or the new Admin routes. A corrective Luna pass added genuine integration tests
(tb4-notification-outbox.integration.test.ts, admin.test.ts,
notification-delivery.integration.test.ts) matching the plan's §10 requirements.

## Bug found during that same verification, before any Sol round

`deleteProjectComment` (workers/app/src/lib/project-comments.ts) used a `changes() === 1` guard for
both its own success check and its audit-log insert. `project_comment_mentions` has
`ON DELETE CASCADE`, and this D1 runtime's JS-level `.meta.changes` field (unlike the documented
SQLite C-API `changes()` semantics) includes cascade-deleted rows — empirically verified at
`.meta.changes === 3` for one comment plus two mentions. This made every delete of a commented-on
comment with mentions throw a false "Comment could not be deleted" error and silently skip its
audit_log entry. Fixed: the outer check became `< 1`; the SQL-level audit guard (a different
mechanism, later empirically confirmed to still correctly return exactly 1 for the same delete)
stayed `= 1`.

## Sol round 1 — verdict REVISE, 9 findings, all confirmed and fixed

High: (1) `suppressWholeOccurrence`/`suppressEmailChannel` in notification-delivery.ts updated
ledger rows without checking outbox lease ownership, letting a stale consumer suppress a live
owner's in-flight channel; (2) `deliverInApp`'s notification INSERT ran unconditionally before its
ownership-guarded ledger convergence check, so a consumer that lost ownership could still commit a
notification; (3) Admin replay/discard lacked any shared-state guard, so both could return 200 on
the same row; (4) replay's audit insert used `changes() = 1` but its preceding ledger UPDATE can
legitimately affect 2 rows (both channels) in the default case, silently skipping the audit.
Medium: (5) a non-self mention with no eligible authorization snapshot at occurrence time was
silently skipped instead of getting a suppressed-by-design outbox row; (6) `safePayload` didn't
validate the outbox row's own schema_version/event_type, and `resolveRecipient` didn't cross-check
`mention.comment_id`; (7) several paths (config-missing, DLQ, Cron, Admin discard) never mirrored
their terminal email outcome into the legacy `notifications.email_error` field, and the mirrors
that did exist ran unconditionally rather than gated on the guarded ledger UPDATE actually winning
ownership. Low: (8) unknown-email discard lacks a specific UI warning (accepted as out-of-scope
Low debt); (9) checked-in evidence files were stale (addressed by this file and the two corrected
files alongside it).

## Sol round 2 (final Sol round; pipeline caps Sol at 2 rounds) — verdict REVISE, 5 more findings

Medium: a selective in-app-only replay never called `completeIfTerminal` when email was already
terminal, leaving the outbox stuck in `processing` forever and endlessly re-reclaimed by Cron;
Admin discard could flip a `suppressed` ledger channel to `discarded`, making it replayable again
even though it was correctly, intentionally suppressed; the optimistic-concurrency `updated_at`
fence in replay/discard wasn't strictly monotonic under same-millisecond collisions; Cron's
round-1 email-mirror fix was unbounded and not coupled to what its guarded UPDATE actually
transitioned. Low: `safePayload` accepted any non-"admin" `authorizationAtOccurrence.kind` as if it
were "project_member". All 5 fixed; see the corrected code and domain-transaction/
authorization-email-classification evidence files for the precise reasoning on the `changes()`
distinction Sol also raised in this round.

## Opus final-draft review — verdict APPROVE

Independently traced the full claim/lease/token fencing, the email-status invariant across
consumer/DLQ/Cron/Admin, the migration, the privacy allowlist, and the test assertions; confirmed
every prior fix genuinely correct and found no other `changes()`/cascade-class bug. Four Low,
non-blocking findings remained (an Admin discard EXISTS-fence asymmetry that could leave an
unaudited mutation in a narrow case; a cosmetic missing error-code in the Admin API's safe-code
allowlist; a narrow DLQ-vs-replay race with no data-loss risk; a misleading-but-harmless audit
record in one crash-recovery path). Only the first was fixed (a one-clause EXISTS addition); the
other three were accepted as low-risk debt.
