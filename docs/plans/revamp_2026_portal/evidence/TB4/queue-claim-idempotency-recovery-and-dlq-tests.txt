TB4 Queue claim / idempotency / recovery / DLQ evidence (2026-08-26)

The passed TB4 contract assertions cover:

  6. The outbox claim UPDATE and in-app-only reclaim UPDATE are the two ordered statements of
      one D1 batch, using the new lease token and EXISTS token fence. The claim includes
      available_at <= now and the email-processing NOT EXISTS fence.
  11. Wrangler config has main max_batch_size 1, max_concurrency 1, max_retries 3 and the
      dedicated DLQ max_batch_size 10/max_retries 3.
  12. Cron performs the four recovery phases, resolves ambiguous email, resets safe in-app work,
      releases other expired claims, and selects only due pending or 30-minute queued-stuck work.
      The publish-candidates phase and the email-ambiguity-resolution phase are both bounded to
      NOTIFICATION_RECOVERY_LIMIT (100) rows per tick. The email-ambiguity mirror into
      `notifications.email_error` is scoped to exactly the rows a `RETURNING` clause confirms were
      actually transitioned in that tick (Sol round 2 fix) — the original round-1 addition of this
      mirror was unbounded and could mirror a row that a concurrent in-flight consumer had already
      resolved differently.
  16. In-app failure releases the in-app ledger before the outbox lease and only then retries;
      a future-available duplicate uses retry({ delaySeconds }) rather than early claim/ack.
      A crash/failure genuinely ambiguous after email enters `processing` (as opposed to a plain
      synchronous send() rejection, which resolves immediately per item 9) leaves the lease in
      place for Cron/DLQ to resolve; the corrective test pass added a dedicated integration test
      simulating this exact scenario via a forced D1 failure on the classification write itself.

The source audit also confirms routing by quincy-notifications and
quincy-notifications-dlq before the existing rendition/ingest paths. Queue message IDs do not
occur in the semantic identity or D1 idempotency keys.

notification-delivery.integration.test.ts) runs and passes outside any codex sandbox; see
automated-gates.txt. No Queue was provisioned or contacted against real Cloudflare infrastructure
as part of this pass — that remains a separate deployment step.
