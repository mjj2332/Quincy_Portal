### A4. Uploader flow
State lives in `lib/video-upload-store.ts`, a module store read with `useSyncExternalStore`, keyed by `(principalId, projectId)`. This is a
deliberate departure from #494's editor-scoped uploads. A 2 GB upload must survive switching Workspace tabs, because `CollectionTabBody` is
keyed by collection (`ProjectWorkspace.tsx:575`) and remounts. It must also survive closing the Project sheet.

Lifecycle of the store:
- A principal change aborts and clears every upload, in the store's own principal-read (render-time), **not** in an effect. See lesson
  "An effect-only fix to a module singleton's identity scoping still has a gap…" (#217).
- `clearPrincipalProjectData` (401) also aborts.
- `beforeunload` warns while any upload is running (#494 lesson).

**Pick → probe**:
1. **Extension and size pre-check (story 7):** the name must match `/\.mp4$/i` (the reserve schema requires it, **(4b)**
   `video-upload.ts:36`), else show the `not_mp4` copy. `file.size > VIDEO_MAX_BYTES` (2,000,000,000, `video-mp4-probe.ts:7`) → show
   `mp4RejectMessage("too_large")` (`:73`). No request is made.
2. **Client probe (stories 8–10):** `probeMp4({ size: file.size, read: (o, l) => file.slice(o, o + l).arrayBuffer().then((b) => new Uint8Array(b)) })` (`:152`).
   - `!ok` → show `mp4RejectMessage(reason)` inline and do not reserve. This saves a doomed 2 GB upload; the server stays the truth.
   - `ok` → show the probed fps, dims and duration on the form ("Frame rate and timecode are read from the file", design Main.dc.html:56).
   - `probe.fastStart === false` → a **non-blocking caution** on the row (story 9): "This MP4 isn't fast-start, so playback may take a moment
     to begin. Re-export with 'fast start' / 'optimise for web' to fix it."
   - `warnings ∋ timecode_rate_mismatch` → caution: "The file's timecode track doesn't match its frame rate, so it is ignored and timecode
     starts at 00:00:00:00."
3. **New film:** the form asks for a title, prefilled from the filename without `.mp4`, trimmed, 1–200 characters. There is **no rename
   route** (see C). **New Version:** no title.

**Reserve**: `POST /api/projects/:p/video-uploads` with `{ title | videoId, filename, bytes, contentType: "video/mp4", clientProbe: { fps, frameCount, width, height, durationMs, codec } }`.
These are exactly the keys **(4b)** `clientProbeDisagreement` diffs (`video-uploads.ts:214-222`); the server re-probes and audits the diff. The reserve schema types `clientProbe` as a loose `z.record` (**(4b)** `video-upload.ts:39`, size-capped), so a shape slip does not 400. It does, however, register as a false disagreement in audit. The values must therefore be **the probe's own shapes**: `fps` is the `{ num, den }` rational from `probeMp4`, not a float, and `codec`, `frameCount`, `width`, `height` and `durationMs` are passed through unchanged. Copy them from the `Mp4Probe` result; do not re-derive them.

Error copy comes from the server body via `messageFromPayload` (`lib/api.ts:12-24` picks `message` → `error`):
| Response | Behaviour |
|---|---|
| 413 `too_large` | show the message |
| 415 | show the message |
| 409 `upload_in_progress` | `"{uploader.name} is already uploading a new version of this video"`; the card also shows it from the DTO |
| 409 `video_service_missing` | show the message |
| 409 `project_archived` | show the message, then invalidate `detail` |
| 429 `too_many_uploads` | show the message |
| 503 | "Uploads aren't available right now." |

The client also caps itself at 3 running uploads per (principal, Project), to match `VIDEO_UPLOAD_MAX_ACTIVE_PER_USER` **(4b)** `video-upload.ts:13`. Despite its name, the server counts it **per user per Project**: **(4b)** `video-uploads.ts:100-101` filters `r.project_id = p.id AND r.created_by = ?`, and the 429 copy says "in this project". The server 429 stays the real limit; the client cap only avoids a pointless request.

**Bytes**: `uploadMultipartFile(file, presign, `${base}/${reservationId}/direct`, undefined, control)` (`lib/multipart-upload.ts:45`).
Parts go one at a time over XHR with byte progress (`:70-95`). `devDirect` takes the single-PUT path (`:73-77`), which is what local QA uses.
- **Per-part retry (story 6), the one change to `multipart-upload.ts`.** Add an opt-in field `UploadControl.retry?: { attempts: number }`.
  - It sits inside `uploadWithControl` (`:70-95`), not in a wrapper, because the loop owns `finished` (the progress baseline) and the abort
    check.
  - Opt-in keeps #494's embedded-video behaviour and tests byte-for-byte. Embedded video can opt in later with one line, recorded as a
    follow-up.
  - **Retry when:** status 0 (network, timeout or CORS), 408, 429 or 5xx. The same part URL is reused (URLs live 6 h:
    `EMBEDDED_VIDEO_PART_URL_TTL_SECONDS`, `packages/shared/src/embedded-media.ts:43`).
  - **Backoff:** 1 s / 3 s / 9 s through the abort-aware `sleep(ms, signal)` already in `lib/embedded-media.ts:100`. Export it or move it to
    `lib/sleep.ts`.
  - On a retry, progress for that part resets to the `finished` baseline.
  - **No retry on 403** (expired or invalid signature). Fail with "This upload took too long and its upload link expired. Start it again."
  - 4d passes `attempts: 3`.
- Cancel works through the shared `AbortController` (story 5). `putOverXhr` aborts the in-flight part (`:26-43`).

**Poster**: `captureVideoPoster(file)` (`lib/video-poster.ts:27`) runs alongside the bytes. It never throws and returns null on failure.

**Complete**: `POST …/:reservationId/complete` with `{ parts }`, or `{}` for devDirect.
- 201 or 200 → `{ video, version, warnings }`.
- Show the server `warnings` too (story 9): the server's verdict wins and can differ from the client probe.
- 422 `video_rejected` → show `message` (`videoUploadRejectMessage`, **(4b)** `video-upload.ts:20`). The row turns failed and has **no
  Retry** (the file must be re-exported).
- 503 `probe_unavailable`, 409 `completion_failed`, or a network error → automatic re-POST of complete (the route is re-entrant, **(4b)**
  `video-uploads.ts:252-263`): 3 tries at 2 s / 5 s / 10 s. After that the row offers **Retry finishing**, which re-POSTs complete and does
  not re-upload.
- 409 `upload_unavailable`, or 400 `upload_missing` on multipart → failed, then abort.

**Poster PUT**: `PUT /api/projects/:p/video-versions/:assetId/poster` with `content-type: image/jpeg` once complete has returned
`version.assetId`. **Any failure is ignored** (stories 12–13). Then invalidate `videos`.

**Abort** follows `lib/embedded-media.ts:262-263,288`: `POST …/abort` with `keepalive: true`, at most once, on cancel or on any terminal
failure after reserve.
- 409 `upload_completed` means the cancel lost the race. Treat it as done and invalidate.
- 503 `abort_pending` means the sweep finishes it. Show "Cancelled".

**Done**: success toast "v{n} of {title} uploaded"; invalidate `videos` and `activity`. 4b writes `project.video.version_uploaded`,
**(4b)** plan item "Activity".

Cards show upload state for both kinds of upload:
- **My upload:** the card shows "Uploading v{n} · 42%" from the store.
- **Someone else's:** the card shows "{name} is uploading v{n}" from `video.uploading`, with no Upload button.
- **Known gap:** a *new film* that someone else is uploading is invisible until it completes. The 4c list maps `uploading` only onto existing

### A5. Player
**Mount and URL.** The viewer opens from local state in `VideoCollectionPanel` (`openVideoId`, `openAssetId`). This follows the Lightbox
precedent: `ProjectWorkspace.tsx:89-90`, `:644-645`. Nothing writes the URL, because the staff route grammar accepts only `arrivalTab` and
`whiteboard` (`packages/shared/src/staff-routes.ts:190`, parser `:314-319`). Navigation calls such as `useNavigate` silently no-op
(`lib/staff-history.ts:102-109`, guard `lib/routing-transport.guard.test.ts`). A deep link is a later slice through the `staff-routes.ts`
parser (see C, decision 2).

The viewer is `lazy()`, wrapped in `components/ViewLoadBoundary.tsx` (lesson "A stale lazy chunk after a deploy took down the whole shell;
every `lazy()` view needs a boundary (#292, 2026-09-28)"). Focus returns to the "Open review" button through Base UI's default `finalFocus`
(`docs/maps/base-ui.md`).

**`useVideoFrameClock(video: HTMLVideoElement | null, version: VideoVersionDto)`**, the interface 5b, 6b and 7 compose on:
```ts
type FrameClock = {
  frame: number;            // last frame known to be on screen (confirmed by rVFC, else derived from currentTime)
  targetFrame: number|null; // a step/seek in flight
  confirmed: boolean;       // true once rVFC (or `seeked` in fallback) has reported `frame` for the current target
  playing: boolean; rate: number; // signed shuttle rate (negative = emulated reverse)
  seekToFrame(f: number): void;   // clamp → pause → currentTime = frameSeekSeconds(f, fps)
  step(delta: number): void;      // seekToFrame((targetFrame ?? frame) + delta)
  awaitConfirmedFrame(): Promise<number>; // 5b/6b: "pause and confirm the frame on screen" (story 31)
};
```
Wiring uses the shared functions only (`packages/shared/src/video-timecode.ts`):
- **Seeking:** to frame *f*, set `currentTime = frameSeekSeconds(f, fps)` (`:38`, the middle of the frame). Clamp to
  `[0, frameCount − 1]`, and also to `< video.duration` when the element reports a shorter duration (audio and video lengths can differ).
- **rVFC path:** `video.requestVideoFrameCallback((_, meta) => frame = frameAtPresentationTime(meta.mediaTime, fps))` (`:43`). Re-register
  inside the callback and `cancelVideoFrameCallback` on unmount or version change. While paused it fires once after each seek, when the new
  frame is composited. That callback is what sets `confirmed`.
- **Fallback** when `"requestVideoFrameCallback" in HTMLVideoElement.prototype` is false: read `frameContainingTime(video.currentTime, fps)`
  (`:48`). Do it on `seeked` (confirmed), on `timeupdate`, and in a rAF loop while playing.
- **Step coalescing:** a step while `seeking` only moves `targetFrame`. On `seeked`, if the target moved, issue one more seek. This avoids a
  seek storm from key repeat (FreeFrame has no equivalent: `apps/web/hooks/use-video-player.ts` has 250 ms interval sync and no frame
  stepping). Edge cases:
  - stepping at frame 0 or at the last frame is a no-op;
  - `ended` → `frame = frameCount − 1`, paused;
  - play at the end restarts from 0 (the FreeFrame `use-synced-transport.ts:170-178` rule).
- **Initial paint:** on `loadedmetadata`, `seekToFrame(0)` so frame 0 is painted with no poster dependence. Use `preload="auto"` so seeks are
  instant (story 18). The ranged `/media/video/:assetId` from 4c serves it.
- **Readout performance:** per-frame values go through a tiny external store, so only the readout and the slider re-render, not the dialog.

**SMPTE (story 21)**: `framesToTimecode(frame, { nominalFps: v.tcNominalFps, dropFrame: v.tcDropFrame }, v.startTimecodeFrames ?? 0)` (`:65`).

| Key | Action |
|---|---|
| Space, K | toggle play / pause |
| L | play at 1×; repeat → 2×, 4×, 8× (`playbackRate`) |
| J | reverse shuttle −1×/−2×/−4×/−8×, **emulated**. It degrades gracefully on long GOPs and never queues seeks. It stops at frame 0. |
| J while playing forward, L while reversing | slow one step toward pause (NLE convention) |
| K held + J / L | ±1 frame |
| ← / → | ±1 frame |
| Home / End | first / last frame |
| Esc | close the viewer (Base UI Dialog default) |

- Visibility is immutable (settled, `docs/plans/741.md`), so the edit schema has no `visibility` key.

**5 Delete**: one batch decides hard delete versus tombstone atomically. D1 runs a batch as one transaction, so a reply cannot land between
the two statements.
```sql
-- (a) hard delete: no reply by anyone else (cascades own replies and markup through FK ON DELETE CASCADE, 0068:98,138)
DELETE FROM video_notes WHERE id = ?nid AND project_id = ?project AND author_user_id = ?uid AND revision = ?rev AND deleted_at IS NULL AND FENCE
  AND NOT EXISTS (SELECT 1 FROM video_notes c WHERE c.parent_id = ?nid AND (c.author_user_id IS NULL OR c.author_user_id <> ?uid));
INSERT INTO audit_log (...) SELECT ?aid1, ?uid, 'video_note.delete', 'video_note', ?nid, ?metaHard, ?now WHERE changes() = 1;
-- (b) tombstone: the row still exists because someone else replied
UPDATE video_notes SET deleted_at = ?now, body = '', drawing_frame = NULL, revision = revision + 1
WHERE id = ?nid AND project_id = ?project AND author_user_id = ?uid AND revision = ?rev AND deleted_at IS NULL AND FENCE;
INSERT INTO audit_log (...) SELECT ?aid2, ?uid, 'video_note.delete', 'video_note', ?nid, ?metaTomb, ?now WHERE changes() = 1;
DELETE FROM video_note_markup WHERE note_id = ?nid AND EXISTS (SELECT 1 FROM video_notes WHERE id = ?nid AND deleted_at IS NOT NULL);
ARCHIVED_SNAPSHOT_SQL;
```
- `metaHard` = `{ mode: "removed", parentId, assetId, ownRepliesRemoved: n }`. `metaTomb` = `{ mode: "tombstone", … }`.
- `changes()` counts only the statement's direct rows; FK-cascaded rows are excluded. A test pins exactly one audit row.
- A reply has no children, so it always takes path (a).
- **Tombstone body `''`** satisfies `body NOT NULL` (0068:107). The markup row is deleted in the same batch (spec: markup is "deleted
  atomically with its note").
- A tombstoned root refuses replies (409 `note_deleted`) and edits. It can still be resolved or reopened.
- Response: the re-read thread, or `null`.

**6 Resolution**: not author-only, not revisioned. Resolving and an author's body edit must never conflict, so this does not bump `revision`.
```sql
UPDATE video_notes SET resolved_at = ?now, resolved_by = ?uid           -- reopen: SET resolved_at = NULL, resolved_by = NULL … AND resolved_at IS NOT NULL
WHERE id = ?nid AND project_id = ?project AND parent_id IS NULL AND resolved_at IS NULL AND FENCE;
INSERT INTO audit_log (...) SELECT ?aid, ?uid, 'video_note.resolve' /* | 'video_note.reopen' */, 'video_note', ?nid, ?meta, ?now WHERE changes() = 1;
ARCHIVED_SNAPSHOT_SQL;
```
- Already in the target state → 200 with the current thread and no audit (idempotent).
- A reply → 422 `not_a_thread` (pre-read). CHECK `reply_shape` also forbids `resolved_at` on replies.
- Guests cannot resolve (`resolved_by REFERENCES user(id)`, settled).

## C. Risks, traps and open decisions

### Traps (lessons cited by heading)
1. **Router.** "A router that owns the URL will canonicalise it, and canonical is not the same as valid (#52, 2026-09-08)". The player is local
   state. Any `useNavigate`/`<Link>` silently does nothing and fails `routing-transport.guard.test.ts`.
2. **Middleware.** "Hono router-wide middleware leaks across sibling mounts" (lessons line ~159). 5a checks inline; there is no
   `videoNotesRoutes.use`.
3. **Archived writes.** "#527 The Project discussion is read-only on an archived Project". Check up front **and** fence in the batch, archived
   before authorship, and External 404. `hasProjectAccess` lets Admin and Editor through on archived Projects
   (`visible-project-scope.ts:26/36`), so the explicit check is mandatory.
4. **Lazy viewer.** "A stale lazy chunk after a deploy took down the whole shell; every `lazy()` view needs a boundary (#292)". The lazy viewer
   goes inside `ViewLoadBoundary`.
5. **Upload behaviour.** "2026-10-05 — Video in Project discussion (#494)":
   - XHR for byte progress;
   - abort once with keepalive;
   - `beforeunload`;
   - the poster is best effort;
   - the playback-failure box is the same as the player box.
6. **Credentials.** "Presigned provider uploads have two separate trust boundaries (2026-08-24)". Part URLs are bearer tokens. Never log
   them, never put them in a toast or error text, and never keep them in the store after completion. The store holds only `reservationId`.
   R2 CORS already exposes `ETag` (`config/r2-cors.json`). 4d is the first 30-part, 2 GB use, so production verification in the pilot must
   include one full-size upload.
7. **Upload store.** "An effect-only fix to a module singleton's identity scoping still has a gap… (#217 fix round 4, item 3)". Scope the store
   by principal at read time.
8. **Keyboard.** "A focusable child inside a composite that owns keydown is a trap until you say otherwise (#206)". The slider owns arrows,
   buttons own Space and Enter, and a test pins both.
9. **Focus rings.** "`outline-none` + `focus-visible:ring-*` still adds a second focus indicator — the fourth, fifth and sixth time (#219)".
   It applies to the custom transport buttons and the vendored slider thumb.
10. **Touch targets.** "Touch targets: grow a 44px box toward empty space, and inset the focus ring of a first-row control (#697, #698)". It
    applies to the transport row and the card actions on the phone.
11. **Cache keys.** "A cache key that omits one of the query's inputs patches an entry nobody is looking at (#230)". 5b's notes query keys on
    **`assetId`**, not `videoId`. 4d's keys are per-Project.
12. **Query-cache tests.** "Polling the query cache does not prove a component rendered it (2026-09-30)". DOM tests assert the rendered card,
    not the cache.
13. **Transient states in tests.** "Asserting a transient loading state is a race unless the test holds the window open (2026-09-03)".
    Progress and probe states in DOM tests hold a deferred promise open.
14. **D1 errors.** "Recurring drizzle/D1 error-shape trap (2026-07-21)". Validate frames and body in TS, so CHECKs never become 500s.
15. **Migrations.** "No triggers in migrations (2026-09-30, #364)". That is why reply-visibility inheritance is enforced by `INSERT … SELECT`,
    not a trigger. 0068 deliberately has no cross-row CHECK. Any future path that writes `video_notes` (5c paste, 13 guest notes) must reuse
    the same SELECT-from-parent shape. **Recommend a shared SQL fragment** in `lib/video-notes-sql.ts` and a test asserting that the reply
    insert has no visibility bind.
16. **Downstream consumers.** Tombstones and `deleted_at` must be excluded by 5c paste, 8/9 export and 12a guest reads. Note it in each later
    plan.
17. **Probe on the main thread.** It parses up to a 16 MiB moov synchronously (`MP4_PROBE_LIMITS`, `video-mp4-probe.ts:8`), which can jank a
    beat on a large file. Accepted (one-off at pick time). Move it to a Worker only if Agy measures a long task over 200 ms.
18. **rVFC support.** Chrome and Edge, Safari ≥15.4 and Firefox ≥132 have it; older browsers use the fallback. Safari seeking precision with
    B-frames is the main real-world risk, and only Seam 3 screenshots can prove it (row 12).
19. **Dialog Escape.** The Base UI Dialog closes on Escape. 5b's composer and 6b's drawing mode must intercept it through `onOpenChange`
    (reason `escape-key`) first. Record this in the 5b plan.

### Decisions the spec leaves open (recommendation first; items 3, 4, 5 and 10 need the owner's eye, the rest are engineering calls)
1. **Split 4d into 4d-i (data, cards, uploader) and 4d-ii (viewer, player).** Each gets its own browser pass. Alternative: one PR.
2. **Player deep link:** none in 4d (Lightbox precedent). Notifications in 15a need one. Recommend `?tab=video&video=<videoId>` (+`&version=<n>`)
   added to the `staff-routes.ts` parser (`:215-221`, one spelling per value, round-trip test) in 15a.
3. **J (reverse):** emulated reverse shuttle by seek-on-`seeked` (A5). Fallback if the Agy pass finds it unusable on long-GOP files: J jumps
   back 1 s per press, repeat 2 s/4 s. Owner-visible because it is how editors will feel it.
4. **Upload survives tab switch and sheet close** (module store, A4). Alternative: component-local, cancelled on leaving the Video tab, which
   is simpler but loses 2 GB uploads to a tab click.
5. **Video rename:** there is no route, so the v1 title is final. Recommend a small `PATCH /videos/:videoId { title }` (`uploadVideo`, audited)
   in 5b or 11a. The owner decides whether titles may change after a client link exists.
6. **Fast-start:** warn and continue (story 9 says warning). Settled by the spec and listed only so nobody adds a blocking confirm.
7. **Editable note fields:** **body only** in 5a. Moving a note means delete and re-post, which keeps markers, export and paste stable.
   Alternative: allow `startFrame`/`endFrame` edits with the same revision CAS.
8. **Tombstone semantics:** no new replies, still resolvable. 5b hides a tombstone with no replies; there is no automatic purge.
9. **Guest author display in the staff DTO:** name only for now (`display_name ?? "Client reviewer"`); 13 decides whether staff see the
   verified email.
10. **Card note counts** (design chips "5 open notes · 2 internal", Main.dc.html:91-95): recommend a separate 5b endpoint

11. **Composer default visibility** (5b): the design defaults to **Internal** (Player.dc.html:194). That is the safe default, because
    visibility is immutable after posting.
12. **Owner question still open from the epic** (blocks 15a only, not 4d or 5a): spec 91b "Anyone  is notified too" is missing a word.
    Not guessed.
