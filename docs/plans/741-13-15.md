### 2.2 Codes and limits
- 6 numeric digits from `crypto.getRandomValues` (rejection-sampled), TTL 10 min, 5 attempts, single use (ADR 0021 §3). Requesting a new code makes older codes of the session dead: verify reads only the newest row by `created_at` for the session.
- Send limits (one `reserveAttempts` batch; `reserveAttempts` gains a per-reservation `windowMs`, and `ipBucket`'s kind union gains `codesend|codeverify`; email buckets are `sha256(email|windowStart)`, never raw): session 1 per 60 s (`codesend:session:<sessionId>`), email 5/15 min + 20/24 h, link 30/15 min, IP 10/15 min.
- Verify: link 100/15 min, IP 30/15 min, plus the per-code 5. The code check is two statements: `UPDATE guest_email_codes SET attempts = attempts + 1 WHERE id = ? AND consumed_at IS NULL AND expires_at > ? AND attempts < 5 RETURNING attempts, code_hash` (no row = expired/burned → 401 `code_expired`), constant-time verify in TS, mismatch → 401 `code_incorrect {attemptsLeft}`. The sixth try finds no row (CHECK ≤ 5): burned.
- Success batch: audit `review_link.email_verify` fenced on `UPDATE guest_email_codes SET consumed_at=? WHERE id=? AND consumed_at IS NULL AND expires_at > ?` + session fence (no `attempts` predicate: a double-click's two correct submissions would otherwise lose the first CAS; `consumed_at IS NULL` alone yields one winner, and the loser gets 401 `code_expired`, after which the page refetches `GET session`, now verified); `INSERT guest_reviewers … ON CONFLICT(email_normalized) DO UPDATE SET display_name = excluded.display_name` (last write wins: it is that person's current name); `INSERT guest_link_members … ON CONFLICT(link_id, guest_id) DO UPDATE SET last_verified_at, last_seen_at` (**`unsubscribed_at` untouched**: re-verifying never resubscribes); `UPDATE guest_sessions SET guest_id, verified_at, token_hash=<new>` with the generation join. All `WHERE EXISTS (audit)`.
- Identical responses for known and unknown emails: send always 202 with the same body after syntax checks; verify's outcomes depend only on the code row.
- Send failure (binding missing or `send` throws): still 202 (no oracle), audit `review_link.email_code_send` meta `{delivered:false, errorCode}` from the safe E_* list (`routes/admin.ts:108`). Missing `EMAIL`/`NOTIFICATIONS_FROM_ADDRESS` is the same.
- Email normalisation: NFC, trim, lowercase whole address; no Gmail dot/plus folding.
- Sweep (`workers/background/src/index.ts`, the 12a hourly sweep): delete `guest_email_codes` with `expires_at < now − 24 h`.

### 2.3 Code hashing — no new secret
Store `hashPasscode(code)` (PBKDF2-100k, salted, versioned prefix; `lib/review-passcode.ts`). Threat model: online guessing is capped by 5 tries per code and the send/verify limits; a DB leak exposes hashes that are single-use, live ≤10 min and **bound to a session whose token exists only as a hash**, so a cracked code cannot be redeemed without the victim's cookie. A keyed HMAC would only add value against that already-useless offline crack, so 13 needs no Worker secret.

### 2.4 Guest notes

- **Producers** (fenced on the source audit id, only when `notify_client` is on; `INSERT … SELECT` over `guest_link_members m` with `m.unsubscribed_at IS NULL` joined to links that reach the Video/Version live; ids from one tested SQL UUID-v4 expression in `lib/sql-uuid.ts`): `video_added` (11a add Video), `version_granted` (11a grants, new assets only), `public_note` (staff root note, `visibility='public'`), `staff_reply` (staff reply under a public root → guests who authored the root or a reply in it), `video_released` (14a Release → links with a live grant and `allow_download`). Internal notes and replies produce **nothing**. Guest replies don't email other guests (`staff_reply` is the schema's only reply event).
- **Flush** `runGuestDigests` on the existing `0 * * * *` cron (`workers/background/src/index.ts:180`): for each member with pending rows, claim by CAS `UPDATE guest_link_members SET last_digest_sent_at=? WHERE id=? AND (last_digest_sent_at IS NULL OR last_digest_sent_at <= ? - 55 min)`; `changes()=1` owns the slot (≤1 email per hour per link, story 92d). Re-filter at send in one query: link `video_review`, unrevoked, unexpired; gate open with `guest` + `notify_client`; member still subscribed; Video still a live member; Version still live-granted; note still public, live; release still live. No survivors → mark rows `sent_at` with no email. Else mint a fresh unsubscribe token (insert its hash), send, then mark `sent_at`. A failed send leaves rows pending for the next hour. Sweep: pending rows older than 7 days and tokens older than 180 days are deleted.
- **Unsubscribe without a token in a URL query:** the link is `${APP_ORIGIN}/d/unsubscribe#t=<token>`. `GET /d/unsubscribe` serves the SPA shell (master `video_review` on, else stub); `src/guest/GuestUnsubscribe.tsx` scrubs the fragment and auto-POSTs `POST /d/api/unsubscribe {token}` (class `guest-link`, no part gate: it only reduces email; unknown token → stub; IP 30/15 min), then shows "You won't get emails about this review" and a **Resubscribe** button (`{token, subscribed:true}`). One click from the email; a link scanner that runs JS can unsubscribe, which the button reverses. `List-Unsubscribe: <that URL>` header if the binding's `send` accepts `headers`; no `List-Unsubscribe-Post` (RFC 8058 needs the token in the URL). Verified guests also get `PUT /d/api/links/:linkId/subscription {subscribed}` (part `guest`, ④⑤).
- Audit: `review_link.unsubscribe`, `review_link.resubscribe` (actor NULL, meta `{memberId, linkId, guest:{guestId}}`).
