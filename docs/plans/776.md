# #776 — Remove a Version / Video, with Trash, restore and purge (settled plan)

Synthesised from two blind drafts (deep-reasoner: `plan-776-deep.md`, Codex: `plan-776-codex.md`) against the owner's decisions of 2026-10-10 (issue comment). Where the drafts differ, the choice and its reason are stated. Deep's §3 and Codex's §3 read-path inventories are both binding: a builder works through the **union** of the two.

## Decisions taken between the drafts
- **Data model: columns, not a separate entries table** (deep). `removed_at`, `removed_by`, `purge_at` sit on `videos` and `video_version_meta`; `removed_with_video` on meta. Codex's `video_trash_entries` table with claim leases is more machinery than the use needs.
- **`purge_at` is frozen at removal** (Codex). "Days left" never shifts after the owner changes the retention.
- **Current pointer is recomputed** (deep). `RECOMPUTE_CURRENT_SQL` keeps the invariant "exactly one `superseded_at IS NULL` per live Video; none for a removed Video or Version". Collection counts, note counts and reserve SQL then need no reader change. Codex's derive-at-read would touch every `superseded_at IS NULL` reader.
- **Purge uses the existing R2 delete queue** (deep). The rows are deleted and their keys enqueued in `embedded_media_cleanup` in one fenced batch, with a live-key recheck in the drain, so no claim/lease table is needed. Fencing the DELETE on `purge_at < now AND removed_at IS NOT NULL` makes a restore racing the purge atomic.
- **Bundling: individually trashed Versions keep their own clock** when the Video is removed later (deep). A Video restore brings back only the `removed_with_video=1` Versions; the others restore one by one from Trash.
- **Notifications** (Codex). Removal terminally suppresses outstanding deliveries and digest items for the removed subjects, so a restore never replays stale emails. Every send-time check also requires live ancestors (#774 `VIDEO_REVIEW_AUTHORIZED_SQL`).
- **Grants** (both). A grant PUT revokes only omitted *live* grants; grants on trashed Versions are kept and come back with a restore.
- **Version numbers** (both). These are never reused: `videos.version_high_water`.
- **Routes**: `POST …/remove` with a body, not `DELETE` with a body (deep).
- **Media and zip** (Codex). Re-authorise after R2 acquisition and before each zip entry. A stream already flowing may finish; the next request is a 404 or the stub.
- **UI** (deep). Remove sits in a ⋯ menu beside the Version select, and the Trash is a dialog from the Video Collection header. An Undo action on the success toast calls the same restore route.
